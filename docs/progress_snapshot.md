## 0. 项目目标与收口条件（当前口径）

- **demo 收口 = 计划式自动驾驶落地 + 项目开源**（`docs/roadmap.md` #7 / #8）。

- **有意取舍不修**：无物理倒车（负向推进原语）、无碰撞模型（A 碾过 B 是视觉穿过）。
- 编辑器（Steps 0–6 + 吸附 + 空间索引）与信号系统（Step 1–6）**已完成并人工验收**；
  #1 连挂/解挂（含折返/寻路联合场景）与 #2 会话持久化**已人工验收通过**。

## 1. 当前在研究什么（一句话）

让列车"**按计划自动运行**"：**计划归控制车（车厢）所有**（"每个控制车都有一个司机，
有自己的任务，与列车无关"），编组每帧**遴选**并**投影**成 `route`/`goal`，
目标点用 **POI**（最小可行范围 = 只做"有向点"）表达。

## 5. 外部参考（2026-09-10 用户指定）—— ✅ 调研已完成

> **结论已固化：`docs/research_pxpatch.md`**（来源清单 + 逐条结论 + 3 借鉴 + 3 陷阱
> + 4 条待人工确认）。下表保留为"来源台账"。

**三 条可借鉴**：① **"等待"是命令的执行语义**（px-patch 的 `OT_WAIT_COUPLE` 无
suspended 状态，只是每帧执行时不产生位移）——印证我们的 Q13；**但连挂交割指针后必须
显式越过该条 wait 命令**，否则接手方重新进入等待（我们记为新风险 **R10**）。
② **"解挂"是一条命令 + 一个"后段计划从哪来"的策略枚举**，而不是"产生两列车的动作"
（→ 我们的 **Q16**，待研讨）。③ **"执行另一个计划"用双指针**（当前表 + 自己的表与
回归格号）——将来做"计划嵌套/临时借用"时的零成本形态。

**三 条陷阱**：① **参照物本身是"计划归编组"**（单一 primary 车头、无多控制车概念）
⇒ **不能拿它论证/否定我们的多控制车遴选**；它的唯一仲裁是"谁连挂谁"，且**平局刻意
给在位者**（我们记为 **R11**）。② **他们从不"执行期跳过失效命令"**（只有每 20 天
巡检 + 新闻提示）⇒ 我们的"跳过该条、计划保留"是**自己的延伸**，Q11 的出处已就地更正。
③ **解挂后两段共享同一可变计划对象**（`AddToShared`）——与审计 B1 同型风险，**照抄
会与"计划归控制车"直接冲突**。

**4 条待确认**（详见调研笔记 §4）：Q11 出处更正（已改）、**"等待连挂"如何退出循环**
（事件改写指针 vs 空命令占位走完）、**`priority`/id 遴选在连挂后是否易主**（建议加
回归断言）、**站台建模路线差异**（他们的命令字段 vs 我们的 POI 实体，已写进 `poi.md` §8）。

**我们想从里面学到什么（调研问题清单——请逐条给答案 + 出处）**：
1. **连挂/解挂的命令与计划语义**：「前往…并等待 couple」如何被拆成命令？事件如何驱动
   指令指针步进？"挂起"在数据上如何表达（是否真的只是"停在等待命令上"）？
2. **多机车/多控制单元的控制权归属与冲突解决**：我们暂定"`priority` 大者胜 → `wagon_id`
   取小"，他们有没有更好的做法（或反例告诉我们这个简化会在哪里崩）？
3. **调度计划的数据类型与编辑交互**：条目结构、跳转/条件、循环、非法条目（invalid orders）
   的处理与提示。
4. **装货的瞬时结算 + CargoDist 的分配模型**（我们缓办，但要知道设计边界，避免将来返工）。
5. **站台/停靠点如何表达**：对照我们的「有向点 / 路段 / 建筑 = POI 集合」。
6. **他们把什么当原子单位**：列车（编组）vs 车厢——他们为支持连挂/解挂改了哪些数据结构？
7. **自动驾驶的层级划分**：计划 / 寻路 / 信号授权 三层如何分工（对照我们的 Q7 单向管道）。
