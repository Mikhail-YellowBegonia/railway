## 0. 用户提案（原文摘要）

> **当前实现：启发式调度计划**。我们用目标（如车站 A、车站 B）表示调度计划，列车通过
> 寻路算法实时规划出应走的路径。代表实践主要是 OpenTTD。优点是对图变化高度鲁棒且无需
> 适配。缺点是没有确定性，只取理论最优，玩家要通过复杂的路点、信号、甚至可编程信号机
> 来与 Dijkstra 对抗，让列车走出自己想要的路径。
>
> **预期实现：路径级调度计划**。我们用**目标 + 路径**表示调度计划，其中用
> **simple_segment 的集合**表示路径（铁路网可以被完全分割为有限个 simple_segment，
> 且不重不漏），进而可解析为 edge/node 级别的路径。列车**不再需要实时寻路**，但
> **进路预约和等信号灯都照常进行**。代表实践主要是 NIMBY Rails、Transport Fever 等。
> 优点是高度确定，贴合现实。缺点是高度死板，对图变化极其不耐受，需要做大量适配以免
> 悬空引用。对玩家的规划水平要求变高，定义路径的操作成本变高。

**提案自己点出的三个风险**：① 阻止按原计划实现调度计划；② **彻底架空寻路算法**、
切断"调度计划 → 行车"的消费顺序；③ 在做好调度计划功能之前**无法进行任何测试**。

## 1. 代码事实核对（2026-09-10 实测；一条修正了提案前提）

### 1.1 今天已经是"算一次、照着走"——**不是**"每帧寻路"

- 全仓**唯一**跑 Dijkstra 的地方是 `GameLoop._find_route`（`controller/game_loop.py`，
  远场寻路，过滤只用 `SignalTable.passable_topology_only`）；调用者**只有两个**：
  `_issue_path_order`（右键设目的地）与 `_couple_to_hovered`（K 键连挂驶向）。
- `TrainDispatcher.tick` 每帧只做"**预约推进 + 授权边界 + 状态转移**"，
  **不重跑 Dijkstra**（`model/dispatch.py`；Step 5/6 的远场/近场拆分即是为此）。
- 运行期的"路径"**本来就是数据**：`TrainState.occupancy.route: list[DirectedEdge]`，
  由 `TrainEntity.assign_route()` 写入；`session.py` 存档还把它直接落盘。

⇒ **消费端（route → 进路预约 → 授权 → 物理 → 位移）与"路径从哪来"已经完全解耦。**
目标级与路径级的差别只在 **谁生产 route**（Dijkstra 还是计划）。
⇒ 提案风险②"切断消费顺序 / 架空寻路"**在机制上不成立**：route 这一层接口不变。
寻路的角色会从"运行时必需"变成"**计划编辑器的补全器 + 手动指令 + 连挂目标搜索**"
（见 §3），不是消失。

### 1.2 "可完全分割为有限个 simple_segment、不重不漏"——**成立，已用真实存档实测**

`manual_track.geojson`（用户实时存档）：**22 节点 / 24 边**，度数直方图 `{2: 18, 3: 4}`
（**没有死端**）。以"度数 ≠ 2"为切割点切分：

| 段（首→末节点） | 边序列 | 长度 |
|---|---|---|
| 4 → 5 | `[2, 1, 3]` | 400.00 m |
| 9 → 6 | `[6, 5, 4]` | 400.00 m |
| 5 → 6 | `[22, 23, 21, 20]` | 1071.24 m |
| 9 → 4 | `[19, 18, 17, 16]` | 1071.24 m |
| 4 → 5 | `[10, 9, 0, 7, 8]` | 405.29 m |
| 9 → 6 | `[13, 12, 11, 14, 15]` | 405.29 m |

**6 段，恰好覆盖全部 24 条边，不重不漏** ✅（段的两端都是道岔；本图是无死端的闭环）。

道岔处的合法转向：**4 个道岔各 4 个（共 16）** ⇒
**全图"走哪条路"的自由度只有这 4 个点**——路径级计划的**信息量很小**，
贵的是**人机接口**（提案说"定义路径的操作成本高"，此为其量化）。

### 1.3 ⚠ 但"段内可通行"**不自动成立**——分割规则要补一条

`RailNetwork.simple_segment_from_endpoint` 沿"度数 = 2"的节点链行走时**不检查
`turn_allowed`**（纯拓扑遍历）。最小反例（**实测**）：

```python
A(0,0) - M(100,0) - N(100,10)   # M 度数 = 2，M 处约 90° 急折
turn_allowed(M, e1, e2) == False   # 反向也 False（正交被前进半平面排除）
simple_segment_from_endpoint(A) -> (110.0, None, [0, 1])   # 仍当成"一整段"
```

⇒ **正确的切分规则 = 在"度数 ≠ 2"**或**"过境转向不许可"**的节点处都要切**；
切完之后"段"才具备"两端之间有通路"这一性质（路径级计划的基本前提）。
⇒ 现状影响：用户当前存档上这类节点 = **0 个**（实测），所以提案**此刻不咬人**；
但编辑器允许建任意夹角，手工急折会产生这种节点，**必须在"分段/校验"里挡住**。

### 1.4 顺带修正的一处文档错误（纯注释，无行为变化）

`RailNetwork.turn_allowed` 的方法 docstring 仍写"夹角 <= 150°（dot >= 常量）"，
与常量 `TURN_ALLOW_DOT_MIN = 0.0` 和 `>` 的实际语义（**严格 < 90°**）矛盾——
2026-09 改"前进半平面"时只改了模块头注释。**已按实际语义补正**（回归照跑）。

## 2. 两条路线的真实差异（差异不在"有没有寻路"）

| | 目标级（现状） | 路径级（提案） |
|---|---|---|
| 确定性来自 | 代价函数 + 图的形状 | **计划本身** |
| 图变化的后果 | 路径自动换一条（可能不是玩家想要的） | 计划**悬空**（可能整条失效） |
| 玩家表达 | 站点列表（+ 路点/信号去"对抗"） | 轨道级行程 |
| route 生产者 | Dijkstra（下单时一次） | 计划 |
| 失效模式 | "列车走了另一条路"（不易察觉） | "列车不动/计划标红"（显眼） |
| 我们的现成对应物 | `_issue_path_order` + `find_path_from_point` | **尚无**（`poi.md` 的"路段"最接近） |

**重要的中间形态（有成功先例）**：Transport Fever 2 的正式模型是"**站点列表 +
路点（waypoint）**"——玩家社群解决"想走特定路线"的常规手段正是加路点
（见其讨论区 "Selecting a specific route with waypoints"），
NIMBY Rails 才是**显式轨道行程**。⇒ 实务上是**三档**：

1. **目标级**（OpenTTD）：只给站点；
2. **锚点级（半确定）**：站点 + 路点/道岔锚点，**锚点之间仍由寻路补全**；
3. **段级（完全确定）**：整串 simple_segment 写死（提案的形态）。

⭐ **我们的 POI 方案已经跨在两条路线之间**：`docs/poi.md` 的三类 POI 里，
"**无向点**"按定义就是 Waypoint（度数 = 2 的节点），"**路段**"按定义就是
`Simple_Segment`。⇒ 把 POI 当"锚点"用就是第 2 档；把段序列显式化就是第 3 档。
**这是本项目不必二选一的结构性原因。**

## 3. 建议方案（供研讨）：**一份数据结构，三档粒度**

### 3.1 机制与载荷正交 ⇒ 风险③（无法测试）可解

计划条目 = **载荷 + 步进语义**。指针推进、回绕、事件驱动步进（Q13/Q14）、
单一步进者、到达幂等等**机制**与"条目载荷是什么"**无关**。
⇒ **可以先用现有的目标级载荷把机制跑通并回归**，路径级条目只是"更强的载荷"。
⇒ 另外，路径计划可先支持**程序化构造 + 落盘**（测试里直接构造条目，不必先有 GUI）。

### 3.2 两种载荷并存（建议，待拍板）

| 载荷 | route 由谁生产 | 用途 |
|---|---|---|
| `goto(目标)`（目标级） | 寻路（今天就有） | 演示/回归/手动右键指令/连挂驶向；图变化时的"退化路径" |
| `follow(路径)`（路径级） | **计划** | 玩家要的确定性；demo 的"贴合现实"卖点 |

### 3.3 `follow` 的路径**权威表示 = 锚点序列**（而不是一上来就存整串 segment）

- 锚点 = POI / 道岔 / 有向点，玩家操作就是"**点几下**"（对比：段级要逐段点）。
- 锚点之间的路径**默认由寻路补全**；需要完全确定的地方，允许把某一段
  **"钉死"为显式 segment 序列**。
- ⇒ 三档粒度用**同一份数据结构**（路径 = 锚点列表，每个锚点可带"钉死的段"）。
- 理由见 §1.2：全图自由度只在道岔上（本图 4 个点），**"走哪条路"的信息量极小**；
  "操作成本高"贵在**人机接口**，不在逻辑表达。

### 3.4 悬空引用（提案自认的最大代价）：我们已有现成机制

- **段/边是派生的、没有稳定 id** ⇒ 引用必须落在**稳定锚点**上。
- 我们**已经有**跨存档稳定的引用机制：`session.py` 的"有向边**不存 edge_id**，
  存两端节点坐标"（`_directed_to_coords` / `_coords_to_directed`）——路径计划
  复用同一套**几何锚定**即可跨存档、跨编辑保持。
- 再加一条**与现有哲学一致的护栏**：DELETE 现在已经拒绝删除"被列车
  `occupied`/`route` 引用"的边（`GameLoop._train_locked_edges`）；把它扩展为
  "**被任何计划引用的边**也拒绝删除（或提示受影响的计划）"⇒ 悬空引用从
  "运行时崩溃"退化成"编辑摩擦"。**这比同类游戏更贴合我们的"图拓扑不变量"。**

## 4. 待拍板（Q21，三问）

1. **粒度落点**：
   - A **只做锚点级**（锚点 + 寻路补全，即 TF2 式半确定）；
   - B（建议）**锚点级 + 可钉死段**——同一份数据结构覆盖半确定与完全确定；
   - C **纯段级**（提案原形：整串 segment 写死，不做补全）。
2. **是否与 `goto` 目标级条目并存**（建议 A）：
   - A（建议）**并存**：`goto` 继续服务手动指令/连挂驶向/回归，并作为图变化时的退化路径；
   - B 只留路径级：更纯粹，但 demo 会卡在"必须先有编辑器"。

   - A（建议）**拒绝删除被计划引用的边**（与 DELETE 保护一致，最省事、最"本项目"）；
   - B 允许删除 + **计划标红待修**（玩家自己修）；
   - C **自动重算补全**（用寻路修复受影响的那一段，最宽容也最"启发式"）。
