计划式自动驾驶（待办 #7；**demo 要做、设计待研讨**；2026-09-10 用户立项）：

**为什么是最大缺口**：现在列车能"沿已下达的 route 自动开到目标点"（远场寻路
`find_path_from_point` + 运动授权/预约 + `BrakingController` 自动停车），但
**目的地由玩家逐次人工指定**（右键设 goal、悬停车钩下达连挂指令、`↑` 建立
巡航）。同类铁路游戏（OpenTTD / Transport Fever 等）一致的做法是**先定义
计划、再由列车跟随计划运行**，玩家不再重复下"去哪里"的命令——本项目 demo
缺的正是这一层。**但本项目不照抄任何一个游戏**：下面只列待研讨的问题，
**未做任何选型结论**。

**现状事实（研讨起点，均已核对代码）**：
- `route` 是"有向边序列"；`goal` 是 `(edge_id, t)` 几何点（支持 Edge 中途）；
  `_stop_before_m` 支持提前停车量（连挂驶向借它对齐车钩）。
- 运动授权 / 进路预约 / 红灯前等待（`is_holding()` → 绿灯续行）已就绪：
  计划执行中的列车遇红灯会停车等待，计划层无需重复实现这套机制。
- **自动到点停车已实现**（`BrakingController` 连续制动曲线），计划层不必再
  解决"怎么停准"。
- 会话持久化（roadmap #2）已落盘列车运行时状态；**计划若引入，必须同步纳入
  `model/session.py`**，否则又会变成"游戏内容与存档机制脱节"（用户已知风险）。

G 阶段背景与四项任务（待办 #9；**demo 要做、与 #7 绑定**；2026-09-10 用户交代）：

**为什么 G 阶段（Multiple Unit）章节一直是空的**（用户 2026-09-10 说明）：
- **原始担忧**：几乎所有铁路模拟游戏都把**列车（编组）当作最小原子单位**，
  而本项目主张**以车厢为最小单位**。当时的判断是——拆分/拼合列车时，很容易
  沿着常见实践实现，导致**列车元数据、调度计划等"交割"处理不当**。这是一个
  被认真对待的风险点，因此单列 G 阶段准备解决。
- **算错的两件事**：
  1. **顺序倒置**——还没做"计划式自动驾驶"，就先做了连挂/解挂，于是整件事
     的前提反了过来（本来是"先有计划的交割规则，再有编组变化"）。
  2. **风险没有发生**——目前看来连挂/解挂**并没有踩到** G 阶段预料的风险点。
- **参照信息**：列车 C 行驶到车站解体为 A / B 再各自驶向目的地，这个过程很好
  理解；但《狂热运输》《OpenTTD》**都没有引入连挂/解挂逻辑**，这点让用户"心里
  没底"；《模拟火车》系列（2006 年 Trainz 起）做到了，但**闭源商业游戏**，
  核心逻辑无从获知——所以只能自己研讨，不能照抄（与 #7 同一条原则）。

数据结构检查结论（#9 第 1 项，**2026-09-10 已执行**；用户要求：**只汇报、
不立即修复**）：

**A. 检查通过、已确立的不变量（有实测支撑）**
1. **身份与几何往返稳定**：`wagon_id` 与 `WagonConfig` 对象在
   解挂→连挂 往返后顺序、对象同一性完全保持，车头世界坐标不变（<1e-6）——
   与既有回归 `tests/test_couple_ui.py` §1/§1b 一致。
2. **`data_log` 按 `wagon_id` 正确拆分/归并**：front 只拿自己的包、rear 拿
   其余的，连挂后归并回来；日志内的 `wagon_id` ⊆ 编组 `wagon_id`。
3. **父子不互相就地改动**：子段 `occupied` 是独立 list（实测非同一对象），
   父列车的 `wagons` 列表与 `data_log` 在解挂后保持原样。
4. **"编组变化时不存在进行中的指令"由模型强制**：`decouple_at`/`couple_with`
   都断言 `is_parked()`（`controller is None` **且** `route` 为空）——行驶中
   与**信号前等待（holding，`route` 非空）**都被数据层拒绝（实测 RuntimeError），
   不依赖 UI 自觉。这条是 G 阶段风险没爆发的**主要原因**。
5. **预约表按对象身份释放**：`BlockManager.tick_reservations` 以
   `set(trains)` 为准，被替换掉的旧实体（解挂的父、连挂的两段）预约立即清除
   （实测残留 0 条）。`TrainEntity` 无 `__eq__`，身份语义可靠。

**B. 风险与缺口（只汇报，**未修复**；影响面见每条末尾）**
1. **车厢是共享可变对象（别名）**：解挂后 front/rear 与父列车**是同一批
   `WagonConfig` 对象**；连挂后 merged 与两个来源也是同一批。实测就地改
   `wagons[0].mass = 999` 会串味到父列车。当前**无人**就地改车厢配置
   （全仓 grep 确认，只有 `__post_init__` 在构造期写 `coupler_2_pos`），
   故非现行 bug。**影响**：未来的货物/损耗/计划状态**不能挂到 `WagonConfig`
   字段**上，否则会跨编组串味——正确挂载点是 `WagonDataPacket.payload`。
2. **`physics` 实例共享/丢弃且无成文规则**：解挂后两段共享父的 physics 对象；
   连挂后 merged 用的是**前车**的 physics，后车的被静默丢弃（连挂时无任何
   提示或选择规则）。当前所有列车都是 `RealisticElectric()` 默认参数
   （每车一实例、无状态），无行为差异。**影响**：roadmap #3 真实物理一旦让
   不同机车有不同参数，"物理属于编组还是属于机车"必须成文。
3. **列车级元数据在编组变化时全部丢弃、且无交割通道**：实测解挂后两段的
   `goal`/`remaining_to_goal`/`v_target`/`authority_remaining`/`_stop_before_m`/
   `couple_approach_partner`/`controller` **全部为重置值**，连挂后 merged 亦然。
   今天安全（第 A4 条保证编组变化时无指令）。**影响**：**第 3~4 项任务的核心
   约束**——"计划"若挂在 `TrainEntity` 上，解挂/连挂会**静默丢计划**；必须先定
   计划的归属层级（编组级 / 车厢级 / 独立实体+引用）。
4. **`Consist.velocity` / `Consist.acceleration` 是死字段**：全仓零引用
   （除自身定义），永远 0.0，与 `TrainState.v` 构成**双重真源且从不更新**，
   解挂/连挂也不交割。**影响**：命名极易误导（看起来像权威列车速度），建议
   在计划系统落地前明确废弃或接入。
5. **`couple_with(self)` 不被数据层阻止**：实测 `a.couple_with(a)` 不报错 →
   产出的编组里**同一 `WagonConfig` 对象出现 2 次**、`total_mass` 翻倍
   （60→120）、车厢几何重叠。UI 层挡住了（`_couple_to_hovered` 的
   `target_train is front`、`find_couple_pair` 排除自身），但**模型层缺自反
   断言**（`decouple_at` 有越界断言，`couple_with` 只有停车断言）。
6. **`data_log` 的归属规则对"非车厢归属的包"不友好**：`split` 把不在
   `front_ids` 里的包**一律归后段**（实测孤儿包被静默扔到 rear），
   `merge` **不去重**（同一包对象出现在两段日志时合并后重复 2 次）。
   今天无影响——`WagonDataPacket` **全仓从未被实例化**（零生产点），
   `data_log` 恒为空。**影响**：第 3 项任务若想用 `data_log` 承载列车级/计划级
   数据，会踩这两条；反之，`payload` + 稳定 `wagon_id` + 已验证的 split/merge
   是**现成的车厢级元数据通道**（其 docstring 本就写着"未来可存放调度命令、
   状态标记等"），可直接为第 3 项所用。

已知限制与未来方向（非本轮待办，记录认知供后续设计）：
- **调车/倒车能力缺失**（2026-09 #1 验收反馈记录）。连挂/解挂已完成，但
  编组作业局限在"前进对接 + 原方向驶离"：
  - **无物理倒车**（当前**唯一剩余**的调车硬限制）：`advance_occupied_path`
    只沿 route 正向推进，没有负向（倒车）推进原语——列车不能"倒着开"
    （车厢物理位置不动、车尾在前）。将来做真实调车（侧线脱离 / 顶推 /
    倒车入位）必须先补这个原语，再谈交互。
  - **玩家手动掉头入口已提供**（2026-09 临时追加功能 1，`c58e147`；本段
    2026-09-10 修正——此前写的"键盘没有任何原地折返键 / 玩家没有入口主动
    触发它"已过时）：PLAY 模式选中**停放**列车按 `R` 原地折返，**任意位置**
    可用，只要求车身所在段无道岔（`connection_count() >= 3`）。语义只切换
    前进方向、不反转编组。指令场景的折返仍走 `_do_auto_reversal` → 同一个
    `reverse_in_place` 原语（另有两种自动折返：寻路路径含折返边时到死端
    simple_segment 端点触发；`_apply_route_result` 首边不匹配时自动 reverse）。
  - 因此 AB 顺序相连解挂后，A 在 B 前方想"退出去"时：可用 `R` 让 A 先原地
    掉头，再沿新朝向寻路驶离——这**替代了旧文档里"只能沿原方向开、碾过 B"
    的唯一出路**。仍做不到的只是"不换向、直接沿 -x 倒车"；若玩家不折返而
    强行沿原方向寻路且前方就是 B，无碰撞模型下表现为"碾过去"（视觉穿过，
    非碰撞），记录于 CLAUDE「已知限制：调车/倒车」。
  - 判定：剩余限制属**预期内结果，非 bug**——几乎所有铁路游戏都简化或回避
    调车（OpenTTD 无连挂；Transport Fever 用机车头自动对接简化）。本项目
    demo 阶段接受此限制。
