# UI/UX 设计与交互状态规范

> 状态：**权威规格，渐进实施中。**
> `project.md` 记录不可轻易改变的总体方针；本文记录具体状态、输入、提示和组件约定。
> 领域行为仍分别以 `docs/editor.md`、`docs/consist_ui.md`、`docs/poi.md` 等文档为准。

## 1. 范围与非目标

本轮是有限的交互壳层重整，不重写轨道几何、吸附、寻路、计划执行、列车物理或世界空间
渲染。项目已确认 `pygame_gui` 符合预期，允许按需引入；状态与动作层仍不得依赖具体
控件库，以便世界交互、自动测试和未来替换保持独立。

目标：

- 用分层状态机可靠管理模式、工具子状态与屏幕叠加层。
- 让相同动作在 GUI、快捷键、tooltip 和帮助文本之间共享同一份定义。
- 将面向玩家的反馈与详细终端日志分离。
- 新功能优先增加独立 controller/view 组件，避免继续扩大 `GameLoop` 和总 renderer。

非目标：

- 不把世界空间轨道编辑改造成传统表单应用。
- 不因视觉统一而改变已经验收的业务语义。
- 不一次性迁移所有旧 `print()`；按功能路径渐进接入反馈层。

## 2. 状态层级

```text
Application
├── Workspace mode（互斥）
│   ├── IDLE
│   ├── BUILD
│   │   ├── READY
│   │   └── ACTIVE
│   ├── DELETE
│   ├── SIGNAL
│   ├── POI
│   │   ├── BROWSE
│   │   └── DRAFT
│   └── PLAY
│       ├── BROWSE
│       ├── PLACE_TRAIN
│       └── EDIT_PLAN
├── Selection / hover context
└── Overlay stack
    ├── consist panel
    ├── schedule menu
    └── future modal dialog
```

约束：

1. Workspace mode 同时只能有一个；切换模式必须经过统一入口并执行退出清理。
2. 子状态只能由所属模式持有；离开模式后不得残留仍能消费输入的子状态。
3. selection/hover 是瞬时上下文，不与模式混为一谈。
4. overlay 必须有明确焦点和关闭语义；离开 PLAY 时关闭 PLAY 专属 overlay。
5. 计划编辑未正常确认或取消前，不允许通过其它模式快捷键绕过退出流程。

## 3. 输入路由

输入按下列优先级处理：

```text
模态窗口 → 获得焦点的 overlay → 当前工具子状态 → workspace mode → 全局快捷键 → 相机
```

每个玩家动作应有稳定的 action id、显示名称、默认绑定和可用上下文。快捷键只是动作的
一个入口；将来增加按钮或菜单时调用同一动作，不复制业务逻辑。

当前约定：

- `P` 保留给 PLAY / 计划编辑。
- 平行吸附改为 `Ctrl+P`，消除原先永远无法到达的第二个 `P` 分支。
- 底部上下文提示来自集中式动作表，不在各 renderer 函数内重复硬编码。
- 上下文复用允许存在，例如 `Space` 在 PLAY 中表示停车或计划暂停，但必须由更具体的
  状态优先消费，并在屏幕提示中显示当前实际语义。

## 4. 玩家反馈

反馈分为四种，不得再把终端原文整体搬进游戏：

| 类型 | 用途 | 生命周期 |
|---|---|---|
| Tooltip | 解释鼠标下的对象、状态和主要动作 | 随 hover 消失 |
| Context hint | 当前状态下最重要的按键/动作 | 状态持续期间常驻 |
| Toast | 成功、失败、拒绝原因 | 短时显示；警告比成功更久 |
| Persistent status | 计划失效、等待连挂等持续问题 | 条件解除前保持 |

终端或 Python logging 保留完整诊断，包括对象 id、几何量和内部异常。屏内文案面向玩家，
说明“发生了什么”和“下一步能做什么”，避免暴露无帮助的内部细节。

当前第一阶段已提供：

- 集中式 `UIContext → ActionHint` 表；
- 底部上下文操作栏；
- 单条短时反馈消息；
- 操作消息仍同步打印终端，便于开发诊断。

`pygame_gui` 的首个接入切片是顶部模式工具栏：按钮使用与键盘相同的稳定 action id，
GUI 消费的鼠标事件不会继续传到世界画布；窗口改变大小时工具栏重新定位。底部上下文栏
和短时消息暂时保留轻量绘制，待主题、中文字体和布局方案稳定后再决定是否迁移。

## 5. 视觉与布局

绘制层级从后到前：

1. 网格与背景；
2. POI/区域底色；
3. 轨道、信号、列车等世界对象；
4. 世界空间选择、高亮、建造/计划预览；
5. HUD 与非模态面板；
6. tooltip、toast、上下文操作栏；
7. 模态窗口。

世界对象的可点击范围和关键图标继续使用屏幕像素阈值，避免缩放后无法命中。颜色不是
唯一信息来源：形状、位置或文字至少提供一种冗余线索。每个像素都应帮助玩家识别对象、
状态或可执行动作，纯装饰不得压过轨道和状态反馈。

## 6. 渐进迁移顺序

1. 建立本文、动作表和反馈层，修复明确的快捷键冲突。
2. 收拢模式切换与 overlay 清理，补状态转换回归。
3. POI 作为第一个完整样板：草稿、属性、创建/删除反馈使用统一交互层。
4. 迁移计划菜单和编组面板。
5. 按需接入 `pygame_gui` 的面板、表单和标准 tooltip；它只负责屏幕空间控件，不接管
   世界空间绘制与拾取。

## 7. 测试义务

- 纯状态与动作表使用不启动窗口的脚本回归。
- 输入冲突必须覆盖“同键在不同上下文下只有一个消费者”。
- overlay 打开、关闭、模式切换和 Esc 优先级需要回归。
- 世界空间交互与视觉布局仍保留人工 GUI 验收，自动测试不伪造像素级可用性结论。
