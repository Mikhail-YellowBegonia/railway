# POI 与建筑（基础定义）

> **状态：基础模型与第一版交互已实现；声明式计划解析开始实施。**
> 本文记录 2026-09-22 确立的 POI 不变量。POI 是基础设施侧的独立地理数据层；
> 车站、Waypoint、selector 等都是其上的消费者。

## 1. 基础不变量

### 1.1 POI 不依赖任何功能

- POI 不为调度计划、连挂、信号或其它功能定制，只描述基础设施上的可复用地理对象。
- 其它功能可以引用 POI。例如调度计划的 selector 可以先引用 POI，再在计划解析阶段
  根据自身语义选择具体的 node/edge、停车位置和到达方向。
- 车站、Waypoint、站台、编组筛选范围等属于 POI 之上的语义层或集合层，不能倒灌进
  POI 基础模型。

### 1.2 POI 是基本地理要素的集合

- POI 的成员只能来自现有基础地理要素：`Node` 或 `Edge`。
- 一个 POI 可以只包含一个元素，也可以包含多个 node/edge；空 POI 没有意义。
- POI 不复制几何、不创建自己的轨道拓扑，只保存对基础元素的引用。
- POI 的集合关系不代表路径顺序、连通性或可行驶性；这些由引用它的功能解析。

### 1.3 POI 成员没有方向

- POI 对 node/edge 的引用一律无方向。Edge 的两个端点属于同一个无向基础元素，POI
  不记录从哪一端进入、列车朝向或停车方向。
- 方向性由消费者（尤其是调度计划）在解析时加入，而不是 POI 的固有属性。
- 同一个 POI 可以被不同方向、不同计划和不同车辆复用；不因为某个计划的到达方向
  复制成多个“有向 POI”。

### 1.4 固定路径边界

- 确定性条目仍可在编辑期冻结唯一物理目标和 `FixedRoute`。
- 声明式条目可以保留 POI/Station 范围，在激活或当前解析失效时生成新的具体目标和
  路径快照。快照进入执行租约，不写回计划意图。
- 运行期刷新必须产生具体 `node_id`/`edge_id + t + direction` 和可验证路径；不能把
  POI 当作绕过寻路、预约和车钩认领规则的自由目标。
- 架构决策见 `docs/architecture/adr-001-declarative-plan-resolution.md`。

## 2. POI 与上层语义

| 类型 | 基础成员 | 上层用途 | 状态 |
|---|---|---|---|
| **Node POI** | 一个或多个 `Node` | Waypoint、站点位置、道岔集合 | 基础模型允许 |
| **Platform** | 一条连续的一个或多个 `Edge` | 站台/站线范围 | 基础模型允许 |
| **Station** | 一个或多个 `Platform` | 车站、建筑或其它命名设施 | 二层集合已实现 |

“有向点”“停车端”“进站方向”等不再作为 POI 基础类型；它们是计划解析阶段对无向
POI 结果附加的约束或目标表示。

### 2.1 车站

车站不是 Edge 集合，而是对若干 Platform 的命名、组织和筛选语义。例如一个车站
可以包含多个连续的站台 Platform，也可以关联其它 Node POI。车站如何选择可用站台、
如何匹配列车长度和停车位置，属于后续车站/调度层设计。

### 2.2 Waypoint

Waypoint 是 POI 的一种上层语义，通常引用一个或多个 Node。它可以作为计划的路径约束，
但不应把“经过方向”写入 POI；方向由计划解析后产生。

## 3. 调度计划如何指向 POI

```text
调度计划条目（指向 POI / 车站）
        ↓ 解析 / 分配
Station（Platform 集合）
        ↓ 计划语义选择具体成员
具体 node/edge + t + direction
        ↓ 确定性冻结 / 声明式按需解析
FixedRoute 或运行期 Resolution snapshot
        ↓ 运行期
只消费冻结路径
```

- 基础 POI 阶段不接入调度计划、selector 或寻路执行。
- 后续计划可以直接指向 POI；车站等上层对象再解析到其 POI 集合。
- 确定性条目在确认前选出具体目标；声明式条目可以保留集合意图，但每次执行前必须解析
  成具体目标与路径快照。

## 4. 第一阶段实现范围

1. ✅ 独立 POI 数据类型与基础校验，不接入调度计划、selector 或寻路执行。
2. ✅ POI 成员只允许现有 `node_id` / `edge_id`，且不带方向、两类互斥。
3. ✅ 增删查、POI 编辑模式、默认属性、半透明包络显示与会话持久化。
4. ✅ Station 最小 GUI 草稿可从已有 Platform 集合创建。
5. 🟡 `goto_couple` 已能接收 POI/Station selector，并在激活时按默认策略解析当前车钩
   与路径快照；刷新版本、拓扑改写和更多命令的声明式目标继续实施。

当前交互与持久化细节见 `docs/editor.md` §10.6；存档使用顶层 `pois` 数组和坐标反查，
不要求采用 GeoJSON/OSM 的关系或铁路车站标准语法。

Platform 可被一个或多个 Station 引用。删除 Platform 时允许删除，并同步从所有 Station
移除其 ID；若某个 Station 因此不再包含任何 Platform，则该空 Station 同步删除。
Waypoint 当前没有上层引用，删除时直接移除。

## 5. 与寻路和固定路径的边界

### 5.1 方向由计划解析加入

现有寻路状态空间使用有向边，计划可以在解析时生成 `goal_directed` 和固定路线；方向
错误的来路不会命中目标。POI 不参与方向选择，也不需要把方向错误的边写进 POI。

### 5.2 POI 与现有能力的对照

| POI 类型 | 计划解析结果 | 现状 |
|---|---|---|
| Node POI | 具体 `node_id`，再由计划补充到达约束 | 现有节点目标可承载 |
| Edge POI | 具体 `edge_id`，再由计划补充 `t` 与 direction | 现有边目标可承载 |
| 多元素/车站 POI | 先选出一个具体成员，再进入上述两种解析 | 需要明确选择策略 |

无论选择策略如何，运行期都不能重新从 POI 集合中自由寻路或换目标。

## 6. 尚未定义、但不阻塞基础模型的问题

- POI 的标签和更多可编辑属性。
- POI 成员后续如何编辑，以及一个元素是否需要限制只能属于特定 POI。
- 轨道 split/delete 时 POI 成员的原子改写、失效或删除策略。
- POI 编辑交互、显示样式和权限门禁。
- 车站如何组织站台 POI、如何匹配列车长度、停车位置和可用方向。
- 多成员 POI 的选择策略：玩家指定、固定优先级、最近可达、空闲优先或其它规则。
- 计划引用 POI 后，何时解析为具体 node/edge，以及与 `FixedRoute` 的冻结时机。

这些问题属于 POI 的实现/消费层；不应反过来改变“POI 独立、成员无方向、可由单个
node/edge 构成”的基础定义。

## 7. 外部参考边界

Transport Fever 2 等游戏同样会遇到“一个高层站点对应多个具体站台，但列车最终必须
停在确定轨道”的问题。本项目先接受这一客观限制：第一版必须在计划冻结时选出具体
node/edge。以后若要实现“站内可选任一合适站台”，应新增明确的站台分配/资源锁定层，
而不是让运行期列车恢复灵活寻路。
