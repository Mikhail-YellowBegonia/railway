## 1. 为什么要重想（动机）

现有数据结构把"车厢（Car）"和"列车（Consist/TrainEntity）"的职责混在一起：

- `WagonConfig` 是**可变** dataclass，且混装了"定死的物理属性"与"会变的载货/任务"。
- `Consist` 既持有**车厢级**数据（`data_log`：按 `wagon_id` 归属的数据包），
  又持有**编组级**状态（`velocity`/`acceleration`，实测为死字段）。
- 全部**运行期状态**（`v`/`occupancy`/`route`/`goal`/`authority_remaining`/
  `controller`/`v_target`/`couple_approach_partner`）都挂在 `TrainEntity` 上，
  并被 `model/session.py` 持久化——**编组变化（解挂/连挂）时这些全部被丢弃**
  （见 `roadmap.md` #9-B3 实测）。

这正是 G 阶段当初预设的风险（"以车厢为最小单位"时的元数据/调度交割）在数据结构
层面的表现。**本稿的目标是把职责重新划清，而不是打补丁。**

## 2. 设计设想（用户 2026-09-10 提出）

### 2.1 车厢的根本属性是 `have_control`

用 `have_control` 区分**控制车**与**非控制车**。（现状代码没有这个概念，只有
`WagonConfig.is_powered`（= `P_rated is not None`）兼任"是不是机车"，两者语义
不同——见 §4.2 Q2。）

### 2.2 车厢属性只读，只能自力更新

- **物理属性不可写入**：车厢的（空载）重量、马力、性质等**定死**，不接受列车写入。
- **载货量只能自力更新**（近期不实现）：学习 OpenTTD——能逐节车厢看到载货量。
- **调度计划不可写入**：打比方说，**每个控制车都有一个司机，有自己的任务，与列车无关**。

即：**列车只能读车厢，不能写车厢**；车厢要变，只能自己变。

### 2.3 列车编组不储存任何持久化数据，只汇总

- **汇总物理属性**：收集全体车厢的物理属性（质量、功率…），算出自己的可用加速度，
  再运行动力学逻辑。
- **汇总调度计划**：收集全体**控制车**的调度计划，**遴选后执行**（见 §2.4）。
- **按需向车厢发信**：例如装卸货命令（近期不实现）——但这类消息**一过性**，不持久。

> **"持久化数据"的边界已于 2026-09-10 拍板（Q1 = 方案 A）**：本条的"不储存
> 任何持久化数据"应读作"**不拥有任何域数据**"——**域数据**（物理属性 / 载货 /
> 调度计划）一律归**车厢**所有；而**运行期派生状态**（速度、`occupancy` 窗口、
> `controller`、`authority`、由选中计划投影出来的 `route`/`goal`）**编组可以持有**，
> 随时可重算，存档时作为"恢复位置用的快照"照旧落盘。详见 §5 Q1。

### 2.4 多控制车的冲突：先给最简解法（深层问题暂不回答）

一列车有两节以上控制车时，它们会"各执一词"，可能持有不同的调度计划，该执行哪个？
**用户明确表示这是个复杂要命的问题，在想清楚之前先不回答**，先采用最简解法：

> **每个控制车自带一个优先级（不查重）。出现冲突时按优先级采纳；优先级相同的
> 用 id 大小决断。**

（"不查重"= 允许优先级重复，不做唯一性校验。id 用 `wagon_id`；"取小还是取大"
尚未拍板——见 §5 Q5。）

## 3. 这套设想顺手解决了什么（与审计结论对照）

`roadmap.md` #9 审计列出的 6 条风险，本设想**直接化解其中 5 条**：

| 审计条目 | 现状问题 | 本设想为何化解 |
|---|---|---|
| B1 车厢是共享可变别名 | 同一 `WagonConfig` 对象跨编组共享，就地改字段会串味 | 物理属性**只读**后，共享别名从"隐患"变成"正确的同一性"；会变的状态（载货量）本就该是同一节车厢的同一份状态，**共享是对的** |
| B2 `physics` 交接无规则 | 解挂共享父的、连挂取前车的，后车被静默丢弃 | 物理属性归属车厢后，`TrainPhysics` 只剩"公式集"（无状态），不存在"谁的物理"问题 |
| B3 列车级元数据无交割通道 | `goal`/`v_target`/`authority`/controller 在编组变化时全部丢弃 | **计划归控制车所有**（"司机与列车无关"）→ 编组变化时计划不走编组，天然不丢；编组每帧重新汇总遴选 |
| B4 `Consist.velocity/acceleration` 死字段 | 与 `TrainState.v` 双重真源、从不更新 | 直接删除（编组只汇总，不存状态） |
| B6 `data_log` 归属规则怪癖 | 非车厢归属的包被静默扔到后段；`merge` 不去重 | 车厢级数据**移入车厢自身**（`WagonDataPacket` 不再"托管于列车编组"）→ 拆分/归并记账整体消失，怪癖随之消失 |
| **B5 `couple_with(self)` 无自反断言** | 实测产生重复车厢、总质量翻倍 | **不化解**——仍需在模型层补断言（本稿不修，记在案） |

另外两点现状事实与本设想一致，可直接沿用：

- **汇总式读取已有先例**：`Consist.total_mass` / `total_length` 已是 property，
  `RealisticElectric` 已按车厢遍历累加牵引力——**"动力叠加"（多机车共同出力）
  与"计划单一"（只采纳一辆控制车的计划）并不矛盾**，是两个正交的量：
  牵引按全部动力车求和，计划按优先级取一个。
- **`wagon_id` 已稳定**（uuid 直存、跨存档保持、`reversed_config` 也保留），
  所以"用 id 决断"在跨存档场景下是确定性的。

## 4. 与现状的差距（代码事实，2026-09-10 核对）

| 设想 | 现状 | 差距性质 |
|---|---|---|
| `have_control` 字段 | **不存在**；只有 `is_powered`（`P_rated is not None`），被物理层（牵引）、渲染（`Loco`/`Coach`）、解挂提示（"单节无动力车厢无法自行行驶"）复用 | 需新增字段并把三处用途拆开 |
| 车厢属性只读 | `WagonConfig` 是**普通可变** dataclass；`__post_init__` 会就地写 `coupler_2_pos` | 需改只读（frozen 或私有字段+只读 property + 窄更新接口） |
| 载货量自力更新 | **不存在**（近期不实现，符合预期） | 新增时须定"谁触发更新"（车厢自己没有 tick） |
| 调度计划归车厢 | **不存在**；计划层整体未做（roadmap #7） | 待 #7 研讨；本稿只定"归属权" |
| 编组只汇总、不存持久化数据 | `Consist` 持有 `velocity`/`acceleration`（死字段）与 `data_log`（车厢级数据存编组）；`TrainEntity`/`TrainState` 持有并持久化全部运行期状态 | 见 §5 Q1（**最大分歧点**） |
| 向车厢发一过性命令 | 无此通道（现有"写入"只有 `TrainPhysics` 读、`session` 序列化读） | 待建（装卸货近期不做） |
| 多控制车优先级冲突 | 无优先级概念；多机车只体现为**牵引力叠加** | 需新增 `priority` 字段 + 遴选规则；**牵引叠加保持不变** |

**已确认的死代码（与本稿相关）**：`Consist.reversed_consist()` 与
`WagonConfig.reversed_config()` 自 2026-09 拍板"折返只换前进方向、不反转编组"
后**已无任何调用者**（只有自引用与文档提及）。它们与本设想也冲突（镜像会造出
同一 `wagon_id` 的第二个对象 = 身份重复），去向见 §5 Q10。

## 5. 待研讨问题（**Q1/Q2/Q6/Q8 已拍板**；其余仍**未做结论**，定稿前不要据此写实现）

**Q1 ✅ 已拍板（2026-09-10）：采用方案 A —— 域数据归车厢，位置/速度归"运行期派生"。**

- **域数据 → 车厢拥有**：物理属性（空载重量/马力/性质）、载货量、**调度计划**。
  随车厢走（解挂带走、连挂随车、存档逐车厢落盘）。
- **运行期派生状态 → 编组持有**：`TrainState.s` / `occupancy` 窗口 / `v` /
  `controller` / `authority_remaining` / `v_target`，以及**由选中计划投影出来的
  `route`/`goal`**。它们随时可由"车厢域数据 + 轨道 + 运行期输入"重算，**编组只是
  当前运行期的宿主**；存档时仍写快照（`docs/session_persistence.md` 的位置还原机制
  不变）。
- **不做**方案 B：运动学真值**不下沉**到车厢 → `RigidWagonKinematics` 刚体链
  （单一车头弧长 + 逐节链式求解）与 `session` 的位置还原机制**保持现状，不重写**。

**因此得到的判定规则（新字段先问这一句）**：
> 这个字段是**域数据**（描述这节车厢本身：物理、载货、任务 → 车厢拥有、随车厢走）
> 还是**运行期派生**（描述"此刻这列编组怎么跑"：位置、速度、授权、计划投影 →
> 编组持有、可随时重算/丢弃）？
> —— 前者进车厢且只读（载货量等由车厢自力更新）；后者进编组，**不允许**被当作
> 域数据长期保存或跨编组交割。

**方案 A 的直接后果（供任务 3/4 落地时对照）**：
1. **审计 B3 的消除方式明确化**：计划本身在控制车上；编组的 `route`/`goal` 只是
   选中计划的**投影**。解挂/连挂时投影被丢弃**不是丢数据**——新的编组会按优先级
   重新遴选控制车、重新投影（这正是"司机与列车无关"）。因此 `session.py` 需要
   逐车厢落盘域数据（计划；物理属性已在存），而运行期快照照旧。
2. **不必碰运动学与位置还原**：`TrainState.s`/`occupancy`/`RigidWagonKinematics`/
   `session` 的位置机制按原样保留 → 改动面从"重写运动学"缩小到"**划分字段归属 +
   给车厢加域数据与只读约束**"。
3. **`Consist.velocity`/`acceleration` 判定为违规**（编组持有域数据性质的字段且从不
   更新）→ 按本方案应删除。
4. **`data_log`/`WagonDataPacket` 判定为违规**（车厢级数据却托管于编组）→ 移入车厢
   自身（Q9）。
5. 解挂/连挂的解算**简化**：不再需要"编组级元数据交割"这一整类逻辑，只需要
   "重新遴选 + 重新投影"。

**Q2 ✅ 已拍板（2026-09-10）：四种组合原则上都要支持；控制与动力不在一个层面上。**

- **支持四种**：①控制+动力（常规机车，最常用）②控制无动力（驾驶拖车）
  ③有动力无控制（被推挽的补机/动车组拖车）④都无（普通车厢，最常用）。
- **控制是车厢的决定性属性**（"比较重要"）→ `have_control` 是车厢的一级属性，
  与身份（`wagon_id`）同级，**决定"这节车厢能不能持有并执行任务"**。
- **动力只是物理参数的一部分**（"无足轻重"）→ `P_rated` 与 `mass`/`length`/`bogies`
  同级，归入**物理属性**，只影响动力学汇总，不决定任何"是谁/能做什么"。
- 推论（沿用）：**牵引照旧按全部动力车叠加**；**计划只从控制车中遴选**。
- 落地含义：现有 `is_powered`（= `P_rated is not None`）**不再承担"机车"的语义**，
  渲染的 `Loco`/`Coach`、解挂提示等三处用途要改判为按 `have_control` 或按动力
  分别表达（见 §7 表）。

**Q6 ✅ 已拍板（2026-09-10）：无控制车的段静止；计划只有控制车才能持有。**

- **解挂后无控制车的段 = 静止**（无计划，也就没有可执行的指令）。
- **它不可能"保留"计划**——因为**调度计划只有控制车才能持有**；这不只是取舍，
  而是 Q1/Q2 的直接推论（计划是域数据，只属于控制车）。
- 推论（**2026-09-10 用户确认"基本正确"，并按 OpenTTD decouple 分支补充如下**）：
  连挂时"落选计划"**不存在丢弃/搬移问题**——计划始终留在它那节控制车上
  （"司机与列车无关"），遴选只决定"此刻执行谁的"。**但"挂起"确实存在**，它的
  形态不是"把计划搬走/标记删除"，而是"**指令指针停在一条等待命令上**"。

**Q6 补充（2026-09-10 用户给出参照：OpenTTD 的 decouple 分支版本）**：
- 该分支里有一种调度计划叫「**前往…并等待 couple**」，实际被拆成原版的
  「前往…」+ 新增的「**等待 couple**」；**执行"等待"命令的车就处在挂起状态**。
- 这依赖**事件信号**。低优先级控制车的写法（用户原文示例）：
  1. 前往 A 点
  2. 等待连挂
  3. 空命令（解挂后跳转至此）
  4. 前往 B 点
  列车在 A 点停好时**位于命令 2**，然后挂车、**失去控制权**；过一段时间列车被
  解挂、**控制车收回控制权**，它**仍停在命令 2**——这就需要"**连挂/解挂**"事件
  发出信号，促使控制车**步进到命令 3**，进而执行后续命令。
- **优先级高的控制车没有这个顾虑**：如果它一直持有控制权，顺着写就行。
- ⇒ **由此修订结论**：计划不是"一份意图"，而是"**有序命令列表 + 指令指针**"；
  需要"**等待某事件**"的命令类型；控制权的得与失要靠**事件驱动步进**。
  这同时部分回答了 Q7（遴选/推进会受事件驱动）。

**Q11 ✅ 已拍板（2026-09-10）：悬空引用 → 该条计划跳过不执行，但仍存在。**

参照 OpenTTD 的「**非法的调度计划**」（invalid orders）：引用失效（POI/边被删）
时**不删除计划、不报错中断**，只是**跳过执行**该条，计划本身保留在控制车上，
玩家之后修复引用即可恢复。**因此计划的引用完整性检查是"执行期跳过"而非"编辑期
拒绝"**——这与本项目 DELETE 保护的做法（拒绝删除被列车占用的路段）**策略不同**，
但两者可以并存：DELETE 保护防的是"运行中的列车崩溃"，计划计划层的悬空引用只
影响"这条命令能不能执行"。

**Q8 ✅ 已拍板最小单元（2026-09-10；**尚需完整调研**）：POI 的最小单元是"有向点"。**

用户给出（原文要点）：**POI 最小的单元是"有向点"，即 1 个 node + 1 条 edge，
从 edge 处指向 node；其中 edge 只提供方向、不提供长度**。"有向点"在 GIS 视角上
是一种**带额外属性的点要素**。这样它就能代表诸如"**站台的末端**"、
"**有方向的停车点**"等地理事物。

- **性质**：这是**方向性锚点**，不是线段（edge 不贡献长度，只回答"朝哪边"）。
- **能力**：能表达现状 `goal=(edge_id, t, direction)` 表达不了的东西——尤其是
  **"有方向的停车点"**（进站方向、停车位置、站台末端）。
- **注意**：**POI 尚未经过任何调研**，本定义只是最小单元的种子；任务 2 仍是
  "构思 POI 系统"，仍需完整研讨（可扩展属性、放置交互、与信号/block 的关系、
  与既有 `turn_allowed` 的关系等）。
- **归属（本稿新增的第三类，见 §7）**：POI 属于**轨道/基础设施侧**——挂在 node/edge
  上、随轨道一起编辑与落盘，**既不是车厢域数据，也不是编组运行期状态**。

**Q9 `data_log`/`WagonDataPacket` 的去向？**（方向已由 Q1 判定规则决定，细节待定）
按 Q1 的判定规则应**移入车厢自身**（其 docstring"托管于列车编组"需改），
`ConsistDataLog.split/merge` 与 `Consist.split_at/merged_with` 的数据包记账随之
整体删除；落盘形态见 §7 表末。

**Q10 死代码与折返语义？**（仍待拍板，但判定倾向明确）
`Consist.reversed_consist()` / `WagonConfig.reversed_config()` 已无调用者，且与本
设想冲突（身份重复）→ 建议删除。注意"折返只换方向不改编组"是 2026-09 拍板的语义，
删除不改变该语义。
